# EVA 引擎性能研究（2026-11-05）

## 结论

- **HUD 模式已经接近空闲，JS 引擎没有值得单独做的优化。** Sport 比 Off 只多约 0.5 个百分点的 CPU，Comfort 只多约 0.2 个。原来怀疑的热点（每 tick 扫部件、`car.data()` 复制）确实存在，但全部去掉也只省 0.1–0.25 个百分点。
- **真正重的是 Dash。** 链路流量约 2800 KB/s，占 5500 KB/s 上传预算的一半；HUD Sport 只有约 220 KB/s。Dash 的 tick p99 是 HUD 的 3–4 倍。
- **最有效的两项已经做了（2026-11-05）：**
  1. 弹窗或警报结束时不重传没变的内容：Dash 每次约 5.3 MB → 0 到约 0.2 MB。
  2. 只发真正变化的像素：Dash 流量从 2790 → 约 1115 KB/s（−60%），Sport 从 218 → 约 98 KB/s（−55%）。
- **上游没有性能更新。** 0.3.11 只改视频，0.4.0 对 CPU、GPU、内存没有变化，apps 主分支的 4 个提交都是主题。0.4.0 的价值在稳定性，而且有风险，要在车上单独验证。

以上数字都不是车上测的，见下一节。

## 优化后的实测

和下面的基线同样的方法。CPU 的差异都在测量误差以内，代价是 Node 多存一份各部件和档位图的像素：Dash 约多 3–4 MiB，HUD 测不出。这份内存不计入服务的 16 MiB 预算。

| 模式 | 链路流量（前 → 后） | 弹窗或警报结束时的写入（前 → 后） | Node CPU（前 → 后） |
|---|---|---|---|
| HUD Comfort | 约 0 → 约 0 | 557 KB → 0 | 0.55–0.73% → 0.58–0.65% |
| HUD Eco | 29 → 16 KB/s | 94 KB → 约 6 KB | 0.63–0.76% → 0.52–0.69% |
| HUD Sport | 218 → 98 KB/s | 777 KB → 约 0 | 0.86–1.00% → 0.93–0.95% |
| Dash | 2790 → 1115 KB/s | 5296 KB → 约 233 KB | 2.6–3.8% → 2.9–3.0% |
| HUD + Dash | 3000 → 1210 KB/s | 6057 KB → 约 233 KB | 3.5–5% → 3.4–3.6% |

结束时写入的“后”是 demo 里那一刻刚好变化的部件，这些本来就该发；数值不变时是 0。

改动在 `shared/eva_canvas.js`（`updates` 和新的 `changes`）和 `shared/eva_hud.js` 的 `_updateGear`。比较一次 `speed` 这样的大部件，本机约 257 µs，大约是绘制它（2.7 ms）的十分之一。

## 测量方法和局限

下面到“假设验证”的数字都是优化前的基线。


- 在本机（Apple Silicon，Node 25）跑真实构建的 `dist/eva_hud`，用计数版客户端替换 cluster-render，每个场景 20 秒。探针是一次性脚本，没有进仓库。
- “demo”是模拟驾驶，所有数值一直在变，是压力场景，实车流量应该更低。“静止”是 demo 关闭、没有数据进来，只剩部件扫描。
- 流量的绝对值可信，因为字节数由内容决定，和 CPU 无关。
- **CPU 和耗时只能看相对值。** 车上是 Node 8.16.2，CPU 也更慢，倍数未知。
- **没有测到：** KOMBI 的 GPU 负载（渲染在 KOMBI 上，车机不画这些层）、cluster-render 服务的 CPU、真实链路是否饱和。这些只能上车测。
- 本机 CPU 的重复测量误差约 ±0.1 个百分点（Dash 约 ±0.5），比这更小的差异不能算数。

### 弹窗或警报结束时的尖峰

现在每次都用 force 重画全部部件。超过 16 个矩形时服务会升级成整图写入（`layer.cpp:222`）。

| 模式 | 矩形数 | 实际写入 | 占用预算 |
|---|---|---|---|
| Dash | 24 + 档位 | 3892 + 1404 = 5296 KB | 约 1 秒 |
| HUD Sport | 25 + 档位 | 604 + 173 = 777 KB | 约 0.15 秒 |
| HUD Comfort | 17 | 557 KB（只超限 1 个矩形） | 约 0.1 秒 |
| HUD Eco | 10 | 94 KB | 很小 |

这些重传没有必要：服务一直保留着像素，目标重新挂上时 `attach` 会自动设 `whole_ = true` 整图重写（`layer.cpp:247`）。

## 假设验证

每一项都是在不改 app 的情况下从外部打补丁实测的。

| 假设 | 场景 | 改之前 | 改之后 | 判断 |
|---|---|---|---|---|
| 缓存 `car.data()` | Sport | 0.86–1.00% | 1.21% | 测不出收益，不做 |
| 按 rateMs 扫部件 | Comfort 静止 | 0.55–0.73% | 0.48% | 省 0.1–0.25，但变化要多等最多 200 ms，暂不做 |
| 去掉 `PopupWatch` | Comfort 静止 | 0.55–0.73% | 0.53% | 省 0–0.2，见建议 3 |

| 三项全做 | Dash | 2.6–3.8% | 3.56% | 测不出 |

| **只发变化的像素** | Dash | 2790 KB/s | **1115 KB/s** | −60% |
| **只发变化的像素** | Sport | 218 KB/s | **98 KB/s** | −55% |
| **只发变化的像素** | Eco | 29 KB/s | **16 KB/s** | −45% |
| **不重传没变的内容** | Dash 尖峰 | 2844 KB（矩形） | **412 KB** | 剩下的是 demo 里刚好变化的 `speed`（393 KB）和另一个部件，这些本来就该发 |

其他排除项：

- **字体：** 一个模式的字体加载本机最多 7 ms，全部加载也才 14 ms。解码后的 atlas 最多 9.1 MiB，Comfort 只有 0.6 MiB，也不会留下 JSON 字符串。不是问题。
- **矩形数：** 正常运行时每次唤醒最多 7 个矩形，没有触发整图升级。只有 force 时才超过 16。

## 建议，按优先级

1、2 已完成，3 以后还没做。

### 1. force 不再重传没变的内容（已完成）

`TextCanvas.updates` 在 force 时仍比较 look，相同就跳过；`_updateGear` 同理。重建图层时 canvas 是新的，第一次绘制不受影响。对 Dash 和 HUD 都有效，也顺带消除 Comfort 只超限 1 个矩形的整图写入。

### 2. 只发变化的像素（已完成）

`TextCanvas` 绘制后和上一次的像素比较，只发变化区域的外接矩形；档位图同理。这样 Node 拷贝、服务 memcpy、链路上传都会减少。
`speed` 从 123 变 124 时只有最后一位变，这是收益的主要来源。

### 3. `PopupWatch` 省掉反复打开文件，Off 模式不轮询（约 10 行，低风险）

`openSync` 占 HUD 空闲时间的 9–11%，是最大的单项。保持文件打开，只做 `fstat` 和 `read`，大小变小时再重开。另外现在 Off 模式也在每 100 ms 打开一次日志，没有必要。

### 4. 重新设计 Dash Only 时拆分 canvas（放到那时再做）

`1680×593` 的 canvas 只用了 37%，中间大块透明，而且压在档位图上面。拆开可以把内存从 10.3 MiB 降到约 5–6 MiB，KOMBI 也少混合约 60 万像素。现在做不划算：Dash 是 5 + 警报 3 = 8 层，已到每连接上限，加层要先改警报层的管理。GPU 上的收益也要上车才知道。

### 5. 上车后再决定

- 把 `fps` 从 30 改成 20（`cluster-render.local.conf`）。服务的唤醒频率由它决定，而 app 只有 20 Hz。可能省服务 CPU，要测。
- 按 `rateMs` 扫部件。如果车上 Comfort 的 CPU 占比明显，再做。

### 不建议做

- 缓存 `car.data()`：测不出收益。
- 单独升级 0.3.11：只改视频。
- 用 `r8` asset + effect 省内存：HUD 只用了 1.3–1.5 MiB，没有必要。
- atlas、mesh、`exclusive`：3–8 层时不划算。
- 没有 KOMBI 数据时拿 effect 换 image：不知道哪边更便宜。

## 上游对比

### cluster-render

| 版本 | 内容 | 对我们 |
|---|---|---|
| 0.3.10 | 车上的版本 | |
| 0.3.11（`origin/main`，PR 82） | 视频 GPU copy、重复帧、`repeat` | 没有用。`js/`、`layer.cpp`、`compositor.cpp`、`upload_pacer.h` 都没变 |
| 0.4.0（`origin/hud`） | HUD 让路、预算份额、证据隔离、mapping guard | CPU、GPU、内存没有变化，稳定性有改进 |

**0.4.0 的好处：**

- `hud_yield_slots = 0x322`：弹窗一出现就立刻释放 HUD，1500 ms 后再要。
- HUD 的出错证据不再降低全局上传上限（`compositor.cpp:720`）。
- HUD 有独立的预算份额（最多一半），在 HUD + Dash 下更稳。
- 日志多了 “offer to flush” 的平均耗时，可以用来测车上的性能。

**0.4.0 的风险：**

- HUD 的 strike 上限从 0 变成 2，超过后 HUD 被禁用，而且跨重启。要用 `cluster-render guard-reset` 恢复。我们经常调试，更容易碰到。
- 只允许 `hud_slot = 0x323`、`hud_scene_id = 0x01000400`、`hud_take_over_stock = 0`，否则 HUD 被丢掉。
- JS 客户端要抄一行 `disabled` 参数。

**和我们的兼容性（读代码，未上车）：**

- `panel_scene_id = 0x010004f0` 没问题。`hud_rules` 只检查 HUD，panel 只和 `scene_ids_allowed` 比较，车上的 local conf 已经包含它。上游注释写着两个目标共用场景、不会同时请求，这一点我们已经不同了。
- `hud_yield_slots` 可以替代 HUD 这一路的 `PopupWatch`。Dash 这一路要配 `panel_yield_slots = 0x202`，配置支持，但上游默认是空的，没人验证过。

**一个和性能无关但要注意的推断：** 我们现在弹窗时是 `visible: 0`，目标要等 `hud_linger_ms = 3000` 才释放。上游说 HUD 在弹窗期间还占着，弹窗会被挤到仪表上，这正是之前方向盘切媒体时来回跳的现象。如果 0.3.1 上车后还跳，优先试 0.4.0，或者把 `hud_linger_ms` 调小。

### apps（`bimmer-lab/apps`）

比我们多 4 个提交（`9da5f6d`、`7fbe0d5`、`0009356`、`f475a8c`），都是 M、Sport、Dials 主题和 200 mph 刻度。`hud_text.js` 只加了 `color2` 渐变，`bake_fonts.py` 加了 `stroke`。diff 里没有缓存、节流、脏区相关的改动，没有性能更新。只有想要这些主题时才值得合并。

## 仪表的设计（2026-11-06）

同样的方法，本机模拟驾驶，一次报警。平时上传是报警结束后 12 秒的平均值。上传时间按上限 5500 KB/s 算。都不是车上测的。

|---|---|---|---|---|
| Original | 1033 KB/s | 5028 KB，约 0.9 秒 | 3009 KB | 10.5 MiB |
| D | 920 KB/s | 5028 KB，约 0.9 秒 | 2670 KB | 10.5 MiB |
| C3 | 1082 KB/s | 5028 KB，约 0.9 秒 | 1934 KB | 11.4 MiB |
| E3 | 579 KB/s | 5028 KB，约 0.9 秒 | 1712 KB | 10.8 MiB |
| A | 103 KB/s | 1397 KB，约 0.25 秒 | 326 KB | 5.8 MiB |
| B | 49 KB/s | 1397 KB，约 0.25 秒 | 52 KB | 5.2 MiB |
| C1 | 接近 0，换分钟时才发 | 1397 KB，约 0.25 秒 | 107 KB | 5.6 MiB |
| C2 | 接近 0，换分钟时才发 | 1397 KB，约 0.25 秒 | 5 KB | 5.9 MiB |
| E1 | 431 KB/s | 1397 KB，约 0.25 秒 | 464 KB | 5.9 MiB |
| E2 | 80 KB/s | 1397 KB，约 0.25 秒 | 92 KB | 5.5 MiB |

- **报警卡的主要原因（本机推断，还没上车确认）：** 开始要传两张彩色标题图，结束要重传为省内存丢掉的图。闪烁本身只有约 50 KB/s。
- **工字形设计已经改善的：** 标题图小，平时的图不用丢，报警结束几乎不用发。
- **大字的代价：** C3 的车速和 E1 的油耗都是很大的图片数字，一变就要传，所以比想象的贵。
- **还没做：** 标题改成 shader 加单色贴图、闪烁交给 KOMBI 的时钟、数字改成 shader（bimmer-lab 的 `atext`）。这些都要先确认 KOMBI 支持。整块仪表设计的报警开始没有改善，要等这一步或者拆开大画布。

## 本次已经修改的

新的大字层（`evaword`）淡出后改成 `visible: 0`。原来 `opacity: 0` 的层仍会被绘制并占用目标，现在隐藏后不再绘制，在弹窗或警报结束后也不会被带回来。弹窗或警报结束不重传、只发变化的像素这两项也已完成，见“优化后的实测”。建议 3 以后都没有动。
